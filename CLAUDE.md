# Shop Management & Transparency Portal

## Purpose
My partner manages the shop (expenses, salaries, raw material, orders, cash). I am the owner and need full visibility. Every transaction must be traceable.

## Stack
- Next.js 16 App Router, Tailwind CSS (v4), TypeScript, `src/` directory, `@/*` import alias
- MongoDB (self-hosted on my Oracle Linux server) via Mongoose
- Auth: NextAuth credentials provider (username + password, bcrypt hashing via `bcryptjs`), JWT sessions
- File uploads: saved to a local disk folder (`UPLOAD_DIR`, default `/uploads`, outside `public`), served through an authenticated API route, images compressed with `sharp`
- Charts: Recharts
- Forms/validation: react-hook-form + zod
- Dates: date-fns + date-fns-tz
- Icons: lucide-react
- Deployment: Oracle server, PM2 + Nginx reverse proxy, subdomain with SSL (Certbot)

## Rules
- **MOBILE FIRST**: every page must work perfectly on a 360px wide phone. Bottom navigation bar on mobile, sidebar on desktop. Large tap targets (min 44px), big inputs, numeric keypad for amounts (`inputMode="numeric"`).
- **Currency is PKR.** Store amounts as integers (whole rupees). Display as "Rs 12,500".
- **Timezone: Asia/Karachi** for all dates and "today" calculations.
- **Roles**: `admin` (owner), `manager` (partner), `viewer` (read-only).
- **NO HARD DELETE anywhere.** Use soft delete: `isVoided`, `voidReason`, `voidedBy`, `voidedAt`.
- **Every create/update/void must write to the `AuditLog` collection** with old and new values.
- **Every record stores** `createdBy`, `createdAt`, `updatedBy`, `updatedAt`.
- Entries with a date older than today are flagged `isBackdated = true`.
- Use server actions or API routes with role checks on the server, never trust the client.
- Keep UI simple and clean: white cards, soft shadows, clear red/green for money out/in.

## Modules
Dashboard, Orders, Cash In (Payments), Expenses, Raw Material, Suppliers, Staff & Salary, Staff Advances, Daily Cash Closing, Reports, Approvals, Audit Log, Settings.

## Environment variables
See `.env.example`: `MONGODB_URI`, `NEXTAUTH_SECRET`, `NEXTAUTH_URL`, `UPLOAD_DIR`.

## Notes on this setup
- Next.js 16 has breaking changes versus older versions. Read the bundled docs in `node_modules/next/dist/docs/` before writing Next.js code (see AGENTS.md above). In particular, `middleware.ts` is now `proxy.ts`.
- The scaffold ships with `cacheComponents: true` and `partialPrefetching: true` in `next.config.ts`. With Cache Components, request-time data (cookies, session, DB reads) must be read inside `<Suspense>` or opted into caching deliberately. Decide whether to keep this when building the first authenticated page.
- `next-auth` is the stable v4 line (`4.24.x`), which lists Next 16 as a supported peer. Auth.js v5 is still beta; do not switch without asking.
- The project folder name has capital letters (`khaasDailyExpense`), so the npm package name is `khaas-daily-expense`.
- Uploads folder `/uploads` is git-ignored. Never put uploaded files under `public/`.

## Data layer
- `src/lib/db.js`: `connectDB()` cached Mongoose connection (call it in every server action / route).
- `src/models/*.js` (plain JS, relative imports with `.js` so `scripts/` can load them with node). Import from `src/models/index.js`.
- Computed fields are set in `pre("validate")` hooks, so use `doc.save()` / `Model.create()`; `updateOne`/`findOneAndUpdate` skip them. Order `orderNo` comes from the `Counter` model; `isBackdated` is auto-set from the entry date (Asia/Karachi).
- `scripts/seed-admin.js <username> <password> <name>` creates the first admin (reads `MONGODB_URI` from `.env.local`/`.env`).
- AuditLog writes are NOT automatic on raw Mongoose calls. Write transaction records ONLY through `src/lib/audit.js`: `createWithAudit(Model, data, user)`, `updateWithAudit(Model, id, updates, user)`, `voidWithAudit(Model, id, reason, user)` (reason min 5 chars), `logAudit({...})` for custom actions (approve/reject, users). `user` is what `requireRole()` returns. They: reject viewers, enforce the daily-closing lock, set createdBy/updatedBy, strip protected fields (isVoided, createdBy, etc.), refuse edits to voided records, skip no-op updates, and store old/new snapshots (never password hashes). Errors are `AppError`/`AuthError` with `.status` (423 = locked day); API routes: `return authErrorResponse(err)`.
- Daily-closing lock: while a DailyClosing for a Karachi day has `isLocked: true`, managers can't create/edit/void/move entries on that day (HTTP 423); admin can. Unlock = admin updates the closing (managers are blocked by the same rule). To lock a new model's dates, add it to `DATE_FIELDS` in audit.js.
- Soft delete is enforced on the models (`addVoidFields`): plain `find/findOne/count/distinct/update/aggregate` skip voided records. Opt in with `.setOptions({ showVoided: true })` (aggregate: `.option({ showVoided: true })`), `findRecords(Model, filter, { showVoided: true })`, or an explicit `isVoided` filter. Populate does not bypass it: pass `options: { showVoided: true }` when a reference may point at a voided record. `deleteOne/deleteMany/findOneAndDelete` throw.
- Helpers: `src/lib/dates.js` (`isBackdated`, `todayKarachi`, `dayKey`, `dayRange`, `formatDateTime`), `src/lib/format.js` (`formatPKR` -> "Rs 12,500", western digit grouping). Shared Tailwind strings in `src/lib/ui.js` (don't import values from "use client" files into server components).
- `/audit-log` (admin only): filters by date range (Karachi days), user, collection, action; mobile cards with "View changes" (old red, new green).

## Auth
- NextAuth v4 config in `src/lib/auth.js` (credentials, JWT 7 days, id/name/username/role in session). Login throttle: 5 failures per IP+username per 15 min (in-memory).
- `src/proxy.js` (Next 16 name for middleware) only checks that a session cookie exists; public paths are `/login` and `/api/auth/*`.
- Real authorization is `src/lib/auth-helpers.js`, which re-reads the user from the DB on every request (so deactivation and role changes apply immediately):
  - Server actions / API routes: `requireAuth()`, `requireRole(["admin"])`, `requireRole(["admin","manager"])`. They throw `AuthError` (401/403); API routes `return authErrorResponse(err)`.
  - Pages/layouts: `requirePageUser()`, `requirePageRole([...])` (redirect instead of throwing).
- Writes must go through `src/lib/audit.js` (`createWithAudit` etc., or `logAudit` for custom actions; never log password hashes).
- With Cache Components, every request-time read (session, DB) must sit under `<Suspense>`. `src/app/(app)/layout.js` wraps the whole signed-in app in one boundary; `getCurrentUser()` calls `await connection()` first because next-auth generates a random CSRF token, which can't happen during prerender.
- Signed-in pages live under `src/app/(app)/`; add new modules to `src/lib/nav.js`. `/login` is outside that group.
- `/settings/users` (admin only): add user, change role, reset password, deactivate/reactivate. Admins can't change their own role or deactivate themselves.

## Uploads
- `POST /api/upload` (admin/manager; multipart field `file`) -> `{ url, thumbUrl }`. Verifies it is a real image (sharp), applies EXIF rotation, strips metadata, saves a 1200px-wide JPEG plus a 240px `-t.jpg` thumbnail to `UPLOAD_DIR/receipts/YYYY/MM/<32 hex>.jpg`. Max 10 MB in (the browser shrinks photos first via `src/lib/image-client.js`).
- **Cloudflare R2 storage (env `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME`, optional `R2_PREFIX` default `shop-portal/`, `R2_PUBLIC_URL` is NOT used):** when the four R2 values are set (`r2Enabled()` in `src/lib/r2.js`, S3 API via `@aws-sdk/client-s3`), `saveReceiptImage()` writes the 1200px JPEG and the thumbnail to the bucket under `<prefix>receipts/YYYY/MM/<id>.jpg` and NOTHING to `UPLOAD_DIR`; `uploadExists()` checks R2 then the local folder. The stored URLs stay `/api/files/receipts/...` (so old records and validation are unchanged) and the bucket is only ever read by `/api/files/` after the sign-in check (no public links in the app). With the R2 values empty the app uses `UPLOAD_DIR` as before. `node scripts/migrate-uploads-to-r2.js` copies older local photos into the bucket (idempotent, never deletes). Never put real R2 keys in `.env.example` or git. Tests/seed scripts that must not touch the real bucket: blank the R2 vars (`R2_BUCKET_NAME=`) in the command. Photos are not part of the JSON backup either way.
- `GET /api/files/[...path]` serves them (from R2, else the local folder) to any signed-in user only; segments are whitelisted (no `..`, no dotfiles). Store the returned `url` in `receiptUrl`; use `thumbUrl()` from `src/lib/validation/expense.js` for the small version. Helpers in `src/lib/uploads.js`.
- The photo picker is `src/components/ReceiptInput.js` ("Take photo" = `capture="environment"`, "From gallery" = plain `accept="image/*"`); reuse it for other modules.

## Expenses module (`src/app/(app)/expenses/`)
- Pages: list (`page.js`: DateFilter + category/method/entered-by/include-voided filters, total excludes voided and rejected), `new`, `[id]` (detail, receipt, history from AuditLog), `[id]/edit`. Server actions in `actions.js` (create/update/void, all via `createWithAudit`/`updateWithAudit`/`voidWithAudit`).
- One zod schema, `src/lib/validation/expense.js`, is used by the browser form AND the server action (server re-parses with the real Settings). Rules: receipt required above `Settings.receiptRequiredAbove`; Misc needs a note; no future dates; whole rupees.
- Approval: amount > `Settings.approvalRequiredAbove` -> `pending_approval` for a manager; the admin's own expense is approved immediately (`approvedBy` = self). A manager's edit re-checks the limit (raising an approved expense above it, or editing a rejected one, sends it back to pending). Approve/reject lives in the Approvals module (below). **Pending and rejected expenses are never counted in any total** (dashboard, P&L, expense report, expense list total, cash book, closing); they are shown separately as "awaiting approval, not counted".
- Locked day: managers get no Edit/Void buttons and the actions return the 423 message; admin can still edit.
- **Expense for a customer order (profit per order):** `Expense.order` (optional ref to Order; `null` = none) is chosen in the expense form with `OrderPicker scope="all"` (`GET /api/orders/search?scope=all` = any order, any status; the default search is only open orders with a balance for Receive Payment). `/expenses/new?order=<id>` pre-links one (the "Add expense for this order" button on the order page). The server checks the order exists; the link can be changed or cleared on edit (audit-logged). Auto-created expenses (salary, advance, purchase, supplier payment) can't be linked (they can't be edited). The list card, expense detail and the order page show the link.
- **Staff / supplier on an expense:** `Expense.staff` and `Expense.supplier` (optional refs, `null` = none). In the expense form, category **Salary** or **Staff Advance** shows a required "which staff member" dropdown (active staff; `STAFF_EXPENSE_CATEGORIES` in `src/lib/validation/expense.js`), category **Raw Material** shows an optional supplier dropdown. Choosing one fills "Paid to" with the name (unless the user typed another). The server re-checks they exist and are active (an already-linked inactive person is kept on edit) and drops the staff link for other categories and the supplier link for non-Raw-Material ones. This is a LABEL only: it does NOT create a SalaryPayment/StaffAdvance or change the supplier khata (the form says so and links to Pay Salary / Give Advance / Pay Supplier). Shown as a chip on the list card and a linked row on the detail page.
- **Order profit rules** (`src/lib/order-profit.js`, used by the order page and the report): cost = APPROVED linked expenses only (voided/rejected never count; pending shown separately as "not counted"); revenue = order net amount (a CANCELLED order: only what was received); profit = revenue - cost, margin = profit / revenue; "in hand" = received - cost. One Expense row per money-out, so nothing is counted twice. An order with no costs entered shows 100% profit: the page/report say to check the Spent column.
- Shared data: `src/lib/constants.js` (categories, payment methods), `src/lib/expense-meta.js` (labels/icons). `AuditHistory`/`AuditChanges` in `src/components/` are reusable for other modules' detail pages.
- Login form is `method="post"` so credentials can never end up in a URL if it is submitted before JS loads.

## Orders and payments (`src/app/(app)/orders/`, `payments/`)
- Pages: orders list (tabs Pending/In Production/Ready/Delivered/All with counts, search by name/phone/order no), `new`, `[id]` (summary, status buttons, payment history, Receive Payment, WhatsApp, history), `[id]/invoice` (printable: the app chrome has `print:!hidden`); payments list (date/type/method filters, total received), `new` (searchable order picker via `GET /api/orders/search`; `?order=<id>` pre-links an order), `[id]` (detail + void).
- Money rules live in `src/lib/order-payments.js`: `recordPayment()` and `voidPayment()`. An order's `advanceReceived` means TOTAL received and `balance` = net - received; both are derived from its non-voided payments (`syncOrderTotals()` repairs drift). Overpayment is blocked by ONE atomic database update (safe when two people pay at once); then the payment is created, the totals re-synced and the order change audit-logged. Always use these two functions for payments linked to orders.
- Creating an order with an advance creates the order (received 0) and then an `order_advance` Payment through `recordPayment()`. If that payment step fails, the order is kept and a notice is shown.
- Linked payments must be `order_advance`/`order_balance`; unlinked ones must be `other_income` and need a note. Cancelled orders can't receive payments.
- Status changes (`changeOrderStatus`, allowed moves in `ORDER_TRANSITIONS`) are audit-logged but deliberately NOT blocked by the daily-closing lock (an order from a closed day still has to be delivered). Payments ARE blocked for managers on a locked day; admin can still record or void them.
- Schemas shared by browser and server: `src/lib/validation/order.js`, `payment.js`. Orders can't be edited or voided yet (cancel via status); payments can't be edited, only voided.
- **Furniture photos (optional):** `Order.photos` = up to 6 URLs (`MAX_ORDER_PHOTOS`), added on `/orders/new` with `src/components/PhotoPicker.js` (multi-photo version of ReceiptInput: camera or gallery, uploads each via `/api/upload`, Save is held while one uploads). The server re-checks every URL with `RECEIPT_URL_RE` and `uploadExists()`. Shown as thumbnails on the order page (tap = full size) and printed small (2.5 cm squares, `-t.jpg` thumbnails) in a "Photos" row at the very bottom of the invoice, under "Thank you"; nothing is printed when there are none. The invoice page sets `@page { margin: 0 }` (its article has its own 14 mm print padding) so Chrome/Edge print no header/footer (date, title, page address). Customer name stays required. Photos can't be added or removed after the order is saved (orders aren't editable yet).
- Delivery colours: `deliveryInfo()` in `src/lib/order-meta.js` (red overdue, orange within 2 days). WhatsApp text in `src/lib/order-share.js`; phone normalisation in `src/lib/phone.js`.

## Staff, attendance, advances, salary (`src/app/(app)/staff/`, `advances/`)
- Pages: `/staff` (active staff cards with outstanding advance in red; `?inactive=1` shows all), `/staff/new`, `/staff/[id]` (profile, month calendar via `?month=`, advances, salary history), `/staff/[id]/edit`, `/staff/attendance?date=` (one-tap Present/Half day/Absent; viewers see it read-only), `/advances` (list) and `/advances/new` (Give Advance), `/staff/salary/new?staff=&month=` (Pay Salary; the server recalculates the figures on every selection), `/staff/salary-sheet?month=` (table scrolls inside its own box).
- Money logic is in `src/lib/staff-money.js` (use these, not raw writes): `giveAdvance` (StaffAdvance + Expense `staff_advance`), `paySalary` (SalaryPayment + advance recovery + Expense `salary` for the net amount; no expense when net is 0), `voidAdvance`, `voidSalary`. The auto-created Expense carries `sourceType`/`sourceId`; such expenses can't be edited or voided from the Expenses module (the action refuses), only by voiding the advance/salary payment, which voids the expense too and gives deducted advances back. If a later step fails, the earlier ones are voided again so nothing is left half-created. Approval rule for those expenses: `approvalFields()` in `src/lib/expense-status.js` (same limit as normal expenses).
- Salary maths, `calcGross()` in `src/lib/salary.js`: monthly = wage / days-in-month x (days in service - absents - 0.5 x half days), unmarked days count as worked; daily = wage x (present + 0.5 x half days), unmarked days are NOT paid; days before the join date don't count; rounded to whole rupees. Gross is always computed on the server. Advance deduction is taken oldest-first and stored on the payment (`advanceAllocations`) so a void undoes it exactly; an advance with deductions can't be voided until that salary payment is.
- One salary payment per staff per month; the owner may tick "pay again", which adds only the not-yet-paid gross plus bonus. Future months can't be paid.
- Attendance is stored at noon Karachi (one live record per staff per day) and goes through `createWithAudit`/`updateWithAudit`, so a locked day blocks managers.
- Limitation: standalone MongoDB has no transactions, and the "already paid" check is check-then-write (Next runs one action per browser at a time, so a double tap is safe; two people paying the same person at the same instant is not guarded).

## Suppliers and raw material (`src/app/(app)/suppliers/`, `materials/`)
- Pages: `/suppliers` (search, total due, red/green balances), `/suppliers/new`, `/suppliers/[id]` (khata ledger, newest first with running balance, New Purchase / Pay Supplier / WhatsApp / Edit, void buttons), `/suppliers/[id]/edit`, `/suppliers/pay?supplier=`; `/materials` (filters: date + supplier + include voided; totals), `/materials/new?supplier=`, `/materials/[id]` (items, bill, void, history).
- Balance = opening + sum(purchase totals) - sum(paid at purchase) - sum(supplier payments); positive = we owe the supplier (red), negative = advance with the supplier (green). Computed on the fly in `src/lib/supplier-money.js` (`balancesFor`, `ledgerFor`), never stored. Opening balance is stored signed (the form has a "who owes whom" toggle).
- Money flows (`recordPurchase`, `paySupplier`, `voidPurchase`, `voidSupplierPayment`): the amount paid at purchase becomes ONE `raw_material` Expense; the unpaid rest is supplier due, NOT an expense, and becomes an expense only when paid via Pay Supplier (also ONE `raw_material` Expense). Voiding a purchase/payment voids its expense. Failure of the expense step voids the record again (nothing half-created).
- **No double counting:** every auto-created Expense carries `sourceType` (`staff_advance` | `salary` | `material_purchase` | `supplier_payment`, list in `EXPENSE_SOURCE_TYPES` in `src/lib/constants.js`) and `sourceId`. Reports must total cash OUT from the Expense collection only, and must never add `MaterialPurchase.totalAmount`, `SupplierPayment.amount`, `SalaryPayment.netPaid` or `StaffAdvance.amount` on top of it. For purchases-by-supplier (accrual) use MaterialPurchase on its own. Manually entered `raw_material` expenses (no sourceType) are possible; the expense form warns to use Buy Material instead.
- A bill photo is required when a purchase TOTAL exceeds `Settings.receiptRequiredAbove` (same limit as expenses). Units: pcs/kg/ft/meter/sheet/litre/bundle. Purchases can't be edited yet (void and re-enter). Supplier payments above the amount owed are allowed and show as an advance.

## Daily cash closing (`src/app/(app)/closing/`, `src/lib/closing.js`)
- `/closing?date=` (default today; any past day): live figures, count form, "Close day" (locks the day), closed result, owner-only "Unlock this day" (reason min 5 chars, saved on the record as `unlockReason/unlockedBy/unlockedAt` AND in the audit log), expandable list of every payment/expense of the day, bank/JazzCash/EasyPaisa in/out shown separately. `/closing/history?month=`: days from the first closing to today; red card on a day with a difference, amber warning on days with no closing (or unlocked and not re-closed), month summary.
- Cash in = Payments with method cash; cash out = APPROVED Expenses with method cash (pending/rejected/voided never count; the screen warns about pending cash expenses). Expected = opening + in - out; difference = counted - expected; a note is required when it isn't 0 (browser and server).
- Opening = counted cash of the latest CLOSED (locked) earlier day, PLUS the net cash movement of any days in between that were never closed (so cash from a skipped day isn't lost). The very first closing has no earlier day: opening is `Settings.openingCashBalance` (set in /settings; Rs 0 by default) and only the owner can override it on that form (field, server-checked).
- All figures are recomputed on the server at close; the browser sends `expectedSeen` and the close is refused (with the new figures shown, typed count kept) if entries changed while counting.
- A closing is one DailyClosing per day stored at noon Karachi; closing a reopened day updates the same record (audit-logged). Closing a day locks it through the existing lock in `audit.js`. Order status changes are the one thing that stays allowed on a locked day.

## Dashboard (`src/app/(app)/page.js`, `src/lib/dashboard.js`, `src/components/dashboard/Charts.js`)
- All numbers are computed server-side in `src/lib/dashboard.js` (MongoDB aggregates, voided records excluded). The DateFilter (Today/This Week/This Month/Custom, in the URL) drives only the top cards: Cash in, Cash out, Profit. "Cash in hand" is not period-based (today's count once closed, otherwise live expected cash from `openingFor()`/`dayFigures()` in `closing.js`). The other sections have fixed windows (this month, last 30 days, now).
- Definitions: money in = Payments (any method, cash shown as a sub-line); money out = APPROVED expenses only (pending-approval ones are shown as "awaiting approval, not counted"; rejected never count). Profit = money in - money out (cash basis; no purchases on credit, no receivables). The closing screen uses the same approved-only rule for cash. Auto-created expenses are Expenses, so nothing is double counted; the activity feed skips them (their source record appears instead) and rejected expenses.
- Alerts: yesterday not closed (only once a first closing exists), cash-difference days this month, pending approvals (admin only), overdue orders (not delivered/cancelled, delivery date before today), backdated entries created this week (links to the audit log for admin only; attendance is not counted).
- Charts (Recharts, client components): donut of this month's spending (max 6 segments: the 5 biggest categories that have their own colour, in fixed colour order, plus grey "Other"; Marketing and Misc always fall in Other; a ranked list with amounts and % sits beside it) and a 30-day money in/out bar chart with a "View as table" twin. Category colours are fixed per category from the validated 8-slot categorical palette (`PALETTE`/`SLOT` in the page); in/out use the app's green/red. Keep new charts to this style: legend, tooltip, table twin, no chart-only information.

## Reports (`src/app/(app)/reports/`, `src/lib/reports/`, `src/app/api/reports/[type]/route.js`)
- `/reports` lists the reports; `/reports/<slug>?range=month|week|today|custom&from=&to=` shows one (the date filter + a "whole month" picker; a missing `range` redirects to this month). Slugs: `profit-loss`, `expenses`, `cash-book`, `orders`, `order-profit` (profit/loss per order dated in the range: value, spent, awaiting approval, profit, margin, plus unlinked "other expenses" for context), `staff`, `suppliers`, `activity` (partner activity: OWNER ONLY, page redirects and API returns 403 for others; everything else is open to all roles).
- Every report is built by ONE function in `src/lib/reports/<name>.js` that returns a plain object (shape documented in `common.js`: `summary` cards + `tables` with typed columns + totals). The same object is rendered three ways: web page (`ReportView.js`: summary cards first, then tables that scroll inside their own box; the expense report adds a category > payee > transaction drill-down), Excel (`excel.js`, exceljs: Summary sheet + one sheet per table, real numbers with rupee/date formats, dates written as Karachi wall-clock) and PDF (`pdf.js`, @react-pdf/renderer, A4 landscape; built-in Latin font, so non-Latin text such as Urdu shows as "?" in the PDF only). To add a report: write a builder and register it in `src/lib/reports/index.js`.
- Export: `GET /api/reports/<slug>?format=xlsx|pdf&<same range params>` (same role rules). File names: `<report>-<period>.<ext>`, period = `2026-10` (a month), `2026-11-04` (one day) or `2026-11-02_to_2026-11-07`; e.g. `expense-report-2026-10.xlsx`.
- Definitions (consistent with the dashboard/closing): sales = Payments; expenses = APPROVED Expenses only (pending approval is reported separately as "not included"; rejected never count); never add purchases/payments/advances/salaries on top (they are already Expenses). Cash book = CASH payments in + APPROVED cash expenses out with a running balance; opening = last closed day's count + movement on unclosed days, or worked back from the first closing. Order "delivered in period" comes from the audit log (status changed to delivered in the range). Staff "recovered" = advance deducted on salaries paid in the range; "still owed" and supplier "total due" are today's balances. Partner activity comes from the audit log (attendance marks counted separately; user administration ignored). Web tables show the first 300 rows; exports contain all rows (PDF caps at 2000 per table).

## Forms, toasts, loading states, demo data
- **Toasts** (`src/components/ui/Toast.js`): `ToastProvider` wraps the whole signed-in shell in `(app)/layout.js` (so a toast raised just before `router.push()` survives the navigation). In client components: `const toast = useToast(); toast.success("Expense saved"); toast.error(msg)`. Success 4s, errors 7s, max 3, duplicates not stacked. They sit under the top bar, 44px dismiss button. `VoidDialog`/`ConfirmDialog` take a `successMessage` prop and toast errors themselves; `VoidRecordButton` has `successMessage` too.
- **Double-submit:** every form uses `useSubmitGuard()` (`src/lib/use-submit-guard.js`): a ref blocks a second tap in the same instant, and after a SUCCESS the form stays locked (the page is about to navigate; re-enabling the button for that moment is how duplicates happen). `guard.run(() => action(values), { relock: false })` for forms that stay on the page (settings, close day). A thrown/network error returns `{ ok: false, error }`. Dialogs have their own ref lock. Buttons: `disabled={isSubmitting || guard.busy}`. Invalid react-hook-form submits toast "Please check the highlighted fields". New forms must follow this pattern.
- **Forms start fresh (Cache Components keeps hidden pages WITH their state):** without care, opening "New expense" a second time showed the first expense's values and a Save button stuck on "Saving..." (looked like editing the previous expense). Every form page wraps its form in `<FreshOnVisit resetKey={...}>` (`src/components/FreshOnVisit.js`, keys the form on `router.bfcacheId`: new form on every link/push visit, draft restored on Back) and every form calls `useResetWhenHidden(guard, resetFn)` (`use-submit-guard.js`: after a successful save, when the page is hidden it unlocks the button and clears the fields; edit forms only unlock). New forms must do both. See `node_modules/next/dist/docs/01-app/02-guides/preserving-ui-state.md`.
- **Loading states:** every route has a `loading.js` (37 of them) rendering `PageSkeleton` (`variant` = `dashboard` | `list` | `detail` | `form`). A new page needs its own `loading.js` with the closest variant.
- Minimum sizes: tap targets 44px (links in running text excepted), text never below 12px (`text-xs`); don't use `text-[11px]`.
- `next.config.ts` pins `turbopack.root` / `outputFileTracingRoot` to the project folder (a stray package-lock.json in a parent folder otherwise triggers a warning).
- **Demo data:** `node scripts/seed-demo.js` fills an EMPTY database (5 staff, 3 suppliers, 20 orders (most with expenses linked to them, one loss-maker), 60 days of expenses/payments, purchases, supplier payments, advances, last month's salaries, attendance, 55 daily closings, pending/rejected/voided examples, 21 generated receipt images in `UPLOAD_DIR`, and a matching audit trail) and prints the expected totals to cross-check Reports. It refuses to run with `NODE_ENV=production`, on a database that already has business data, and on a database with real user accounts (use `--use-existing-users` to attach to your own admin/manager; otherwise it creates `demo.owner` / `demo.manager` / `demo.viewer`, password `DemoPass123` or `DEMO_PASSWORD`). Point `MONGODB_URI` at a separate database (e.g. `shop_portal_demo`). Deterministic: same data every run. It writes raw documents (bypassing server actions) but follows the same rules; if you change a money rule, update the script too.

## Approvals, Settings, Backup (`src/app/(app)/approvals/`, `settings/`, `src/lib/approvals.js`, `src/app/api/backup/route.js`)
- `/approvals` (admin only; others are redirected): cards for expenses with `status: "pending_approval"`, oldest first (amount, category, paid to, method, date, backdated badge, receipt thumbnail, entered by, when, note). **Approve** (confirm dialog) and **Reject** (`VoidDialog`, reason min 5 chars). Logic in `src/lib/approvals.js` (`approveExpense`, `rejectExpense`, `pendingApprovalCount`); actions in `approvals/actions.js` use `requireRole(["admin"])`.
- Writes use `logAudit` with action `approve` / `reject` (old = pending, new = approved/rejected + reason), NOT `updateWithAudit` (that would log "update"). Approval sets `approvedBy/approvedAt`; rejection sets `rejectReason/rejectedBy/rejectedAt`. Only a still-pending, non-voided expense can be decided (a second click gets "already approved/rejected"). The daily-closing lock does not stop the owner approving a past day (the card warns that the closing's counted figures don't change).
- Auto-created expenses (`sourceType` set) can be approved but NOT rejected (the UI hides Reject and the server refuses): void the source record (advance, salary, purchase, supplier payment) instead. Texts come from `EXPENSE_SOURCES`.
- A manager editing a rejected expense sends it back to pending (old rejection cleared from the record, kept in audit history). Expense detail shows the rejection reason and an amber "waiting for approval, not counted" note.
- Red count badge (`components/shell/CountBadge.js`): the `(app)/layout.js` Shell reads `pendingApprovalCount()` for admins only and passes `pendingCount` to `Sidebar` (on the Approvals link), `BottomNav` (on the "More" button and the Approvals tile in the More sheet). Create/update/void expense and approve/reject call `revalidatePath("/", "layout")` so it refreshes.
- `/settings` (admin only): form (`SettingsForm.js`, schema `src/lib/validation/settings.js` shared with the server action) for shop name (2-60 chars), receipt-required limit, approval-required limit, opening cash balance (whole rupees >= 0). `updateSettings` uses `updateWithAudit(Settings, ...)` (old/new in the audit log; unchanged save writes nothing) and revalidates the whole layout (shop name, limits). Limits apply to NEW entries only. The page also links to Users and Backup.
- `GET /api/backup` (admin only: 401/403 otherwise) streams `shop-backup-YYYY-MM-DD.json` (Karachi date): header (`exportedAt`, `exportedBy`, `counts`, `note`) + `collections` with EVERY collection (read from the database, so new models are included automatically), voided and rejected records included, extended JSON (`{"$oid"}`, `{"$date"}`), documents streamed one at a time. **`users.passwordHash` is never exported.** Each download writes an audit entry (`collectionName: "backup"`, action `export`). `/settings/backup` has the download link and the last-backup time. Uploaded receipt photos are NOT in the JSON (they live in `UPLOAD_DIR`; back that folder up separately). There is no restore tool yet.
- `getModel()` (models/_shared.js) re-registers a model on every load outside production. Without that, `next dev` kept the OLD schema after a hot reload and silently dropped a newly added field (this lost the first order photos). After adding a field in production-like runs, just rebuild/restart.
- Route segment config `export const dynamic` is rejected by Cache Components: don't use it in route handlers.
